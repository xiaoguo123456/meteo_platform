# 全球天气态势浏览器架构

## 1. 项目定位

本项目用于在一个三维地球上展示多种数值天气预报模型、卫星云图和中国省级边界。第一阶段以研究和展示为目标，优先保证数据链路清晰、界面响应稳定和单机部署简单。

系统需要支持：

- GFS、IFS、AIFS、GRAPES 等公开数值预报数据；
- 风场、温度、气压、湿度、降水和模型云场等天气要素；
- Himawari 等卫星云图，并预留 GOES、Meteosat 接入位置；
- Esri 全球底图；
- 中国省级行政区划边界；
- 模型、预报时效和天气要素切换；
- 时间轴播放、暂停和拖动查看预报变化。

## 2. 约束与设计原则

- 只有一台服务器，不部署 CDN，不拆分微服务。
- 后端负责数据获取、格式统一、预处理和缓存，浏览器不直接解析 GRIB 或 Open-Meteo 专用文件。
- 大文件放在服务器本地文件存储，Redis 只保存短期元数据和任务状态。
- 数据源和地图服务必须遵守各自的授权、署名、访问频率和缓存条款。
- 中国省级边界使用独立的官方或授权数据，不使用底图中的边界线作为最终业务边界。
- 先建设可运行的单机版本，再根据实际数据量和访问量决定是否引入对象存储、CDN 或独立任务节点。

## 3. 总体架构

```text
浏览器
  React + TypeScript + Globe.gl + Three.js
          │ HTTP / WebSocket（按需）
          ▼
单体后端服务（FastAPI）
  ├─ 天气查询 API
  ├─ 云图查询 API
  ├─ 省界与配置 API
  └─ 管理与健康检查 API
          │
          ├──────── PostgreSQL + PostGIS
          │          模型运行记录、任务状态、省界元数据
          │
          ├──────── Redis
          │          最新运行信息、锁、短期查询缓存
          │
          └──────── 本地数据目录
                     天气场、云图、切片、边界 GeoJSON

后台任务进程（同一代码库）
  ├─ 同步 Open-Meteo S3 模型数据
  ├─ 下载和处理卫星云图
  ├─ 提取变量并生成前端数据文件
  └─ 清理过期文件、刷新元数据
```

开发环境可以使用 Docker Compose 启动 API、Worker、PostgreSQL 和 Redis。生产环境仍然保持同样的进程边界：一个 API 进程、一个 Worker 进程和一套数据库/缓存服务。

## 4. 推荐技术栈

### 前端

- React
- TypeScript
- Vite
- Globe.gl
- Three.js
- Zustand
- Web Worker
- 原生 CSS 或 CSS Modules

Globe.gl 负责地球、相机、经纬网、边界线、点线图层和交互容器。Three.js 自定义图层负责风场粒子、粒子拖尾、云图球壳和发光效果。Web Worker 负责风场插值、粒子推进等计算，避免阻塞主线程。

### 后端

- Python
- FastAPI
- Pydantic
- SQLAlchemy
- APScheduler 或应用内任务循环
- xarray
- cfgrib / eccodes
- rasterio
- pyresample

后端只向前端提供统一的数据格式。原始数据解析和前端数据生成放在 Worker 中，API 进程只负责查询元数据、读取已生成文件和返回结果。

### 存储与部署

- PostgreSQL + PostGIS：结构化元数据、任务记录和省级边界信息；
- Redis：短期缓存、分布式锁的替代方案和任务状态；
- 本地文件系统：天气场、卫星云图、前端二进制文件和 GeoJSON；
- Nginx 或 Caddy：反向代理、静态文件和 HTTPS；
- Docker Compose：单机部署和本地开发环境。

## 5. 数据源与接入策略

### 5.1 数值预报

优先使用 Open-Meteo 对应 AWS Open Data 目录中的空间数据。第一批接入：

1. GFS：公开、更新稳定，作为基准模型；
2. IFS：用于与 GFS 做全球预报对比；
3. AIFS：用于展示机器学习预报模型；
4. GRAPES：在确认字段、更新频率和使用条款后接入。

Worker 通过每个模型的最新运行信息定位数据，只读取需要的变量和时间范围，然后转换为统一格式。不要把原始 `.om`、GRIB2 或 NetCDF 文件直接暴露给浏览器。

统一天气场至少包含：

```text
model
run_time
valid_time
variable
level
bounds
width
height
encoding
data_url
```

风场至少需要 `u10` 和 `v10` 两个分量。温度、气压、湿度和降水以单变量网格提供。前端优先使用压缩后的 `Float32Array` 或 `Uint16Array`，而不是 JSON 数组。

### 5.2 卫星云图

中国及亚太区域优先接入 Himawari-8/9，后续按覆盖范围增加 GOES 和 Meteosat。卫星云图和模型云场分别作为两个图层：

- 卫星云图表示当前观测；
- 模型云场表示未来预报；
- 卫星云图默认按 5 至 15 分钟级别刷新，实际周期以数据源为准；
- 云图下载后统一重投影、裁剪、压缩，并生成等经纬度纹理或瓦片；
- 云图文件只保留产品需要的时间窗口，定时清理更早的数据。

第一版使用透明纹理覆盖在地球外侧的云层球壳上。需要更高分辨率或局部放大时，再切换到云图瓦片。

### 5.3 底图

底图使用 Esri 服务。前端或后端只按实际视图请求瓦片，服务器可以在本地做按需缓存，但必须：

- 保留 Esri 及底层数据提供方署名；
- 使用 API Key 或官方允许的认证方式；
- 遵守服务返回的缓存策略、访问频率和额度；
- 不预先批量抓取整个全球瓦片库；
- 不把缓存当成绕过授权或计费的方式。

底图缓存目录按服务、样式、缩放级别、行列号组织，便于设置容量上限和淘汰策略。

### 5.4 中国省级边界

省级边界单独维护为版本化 GeoJSON。数据优先从天地图或自然资源部门公开目录获取，并在使用前确认授权和标准画法要求。处理步骤：

1. 获取省级行政区划数据；
2. 统一坐标系和字段名称；
3. 删除县级及更细粒度要素；
4. 做适度几何简化；
5. 记录数据来源、版本和更新时间；
6. 在 Globe.gl 中作为独立边界层加载。

## 6. 数据处理流程

```text
定时任务
  ↓
检查模型最新运行
  ↓
下载所需原始数据
  ↓
校验文件、记录运行状态
  ↓
提取变量并统一网格
  ↓
压缩为前端二进制文件
  ↓
写入本地数据目录
  ↓
更新 PostgreSQL 与 Redis 元数据
  ↓
API 提供给前端
```

任务必须可重复执行。每个模型运行使用固定目录和状态记录，下载失败时保留上一个可用运行，不能因为一次上游异常清空线上数据。

建议的本地目录：

```text
data/
  raw/                  # 可选，短期保留的原始文件
  fields/{model}/{run}/ # 天气场二进制文件
  satellite/{source}/   # 卫星云图纹理或瓦片
  tiles/esri/           # Esri 按需缓存瓦片
  boundaries/           # 省级边界 GeoJSON
  manifests/            # 文件清单和校验信息
```

## 7. 后端接口

第一版 API 保持简单稳定：

```text
GET /api/health
GET /api/models
GET /api/models/{model}/runs
GET /api/fields/{model}/{valid_time}
GET /api/fields/{model}/{valid_time}/wind
GET /api/cloud/latest
GET /api/cloud/{source}/{time}
GET /api/boundaries/provinces
```

天气场元数据示例：

```json
{
  "model": "ecmwf_ifs025",
  "runTime": "2026-10-12T12:00:00Z",
  "validTime": "2026-10-13T00:00:00Z",
  "bbox": [-180, -90, 180, 90],
  "width": 1440,
  "height": 721,
  "variables": ["u10", "v10", "temperature_2m"],
  "encoding": "float32-gzip",
  "dataUrl": "/api/fields/ecmwf_ifs025/2026-10-13T00:00:00Z"
}
```

数据接口支持 HTTP 压缩和 Range 请求。对于单个变量或局部区域，优先返回较小的二进制文件，避免每次切换要素都下载完整天气场。

## 8. 缓存策略

缓存分为三类：

| 内容 | 位置 | 策略 |
| --- | --- | --- |
| 模型运行信息、任务状态 | Redis | 短期缓存，失败时允许读取上一次结果 |
| 已生成天气场 | 本地文件 | 按模型、运行和有效时间长期保留，按磁盘容量清理 |
| 卫星云图 | 本地文件 | 保留有限时间窗口，按数据源刷新周期更新 |
| Esri 瓦片 | 本地文件 | 按需缓存，设置总容量和最近最少使用淘汰 |
| 省级边界 | 本地文件 + 数据库 | 版本更新时替换，平时长期复用 |

天气场缓存键：

```text
{model}/{run_time}/{valid_time}/{variable}/{level}/{region}/{resolution}
```

Worker 对同一模型运行使用锁，避免重复下载和重复处理。API 遇到文件不存在时不直接同步执行重处理，而是返回当前状态或上一次可用数据。

## 9. 前端页面与渲染分层

页面按以下区域组织：

- 地球主视图：地球、夜间底图、风场、云层和省界；
- 左侧控制区：模型、要素、时间和动画控制；
- 时间轴：运行时间、有效时间、播放和暂停；
- 地图状态：当前模型、要素、云图来源和数据时间。

渲染顺序建议为：

```text
Esri 底图纹理
  ↓
地球本体与大气光晕
  ↓
卫星云图球壳
  ↓
温度/气压等颜色场
  ↓
风场粒子与拖尾
  ↓
中国省级边界与交互标记
```

风场粒子数量、纹理分辨率和动画帧率都需要可配置。低性能设备优先降低粒子数量和数据分辨率，不影响模型切换和时间轴操作。

## 10. 部署方式

生产环境使用一台服务器：

```text
Nginx / Caddy
  ├─ /       → 前端静态文件
  └─ /api/   → FastAPI

FastAPI 进程
Worker 进程
PostgreSQL
Redis
本地 data/ 目录
```

建议使用 Docker Compose 管理进程和依赖。定时任务只运行在 Worker 中，API 进程不承担下载任务。服务器至少需要：

- 足够的磁盘空间保存多个模型运行和云图时间窗口；
- 定期备份 PostgreSQL 和省界数据；
- 对 `data/` 设置容量监控；
- 对上游数据失败、磁盘不足和任务积压提供日志与健康检查。

## 11. 分阶段实施

### 第一阶段：可运行原型

- React、TypeScript、Vite 和 Globe.gl 页面；
- 模拟风场粒子；
- Esri 底图接入；
- 中国省级边界加载；
- 模型、要素和时间轴控制面板。

### 第二阶段：真实天气数据

- 接入 GFS；
- 建立天气场统一格式和本地文件缓存；
- 接入温度、风场、气压和降水；
- 完成 Worker、任务状态和失败回退。

### 第三阶段：多模型与卫星云图

- 接入 IFS、AIFS 和 GRAPES；
- 接入 Himawari 云图；
- 增加云图时间序列、透明度和播放；
- 增加模型对比和数据时间显示。

### 第四阶段：性能与运维

- Web Worker 风场计算；
- 二进制数据压缩和 Range 读取；
- Esri 瓦片容量控制；
- 任务重试、日志、备份和磁盘告警。

## 12. 需要提前确认的风险

- 各模型数据的字段、更新时间、保留周期和授权可能变化，接入器必须保留配置层；
- 卫星云图覆盖范围和时间延迟取决于数据源，不能把不同卫星简单拼成无缝全球产品；
- Esri 底图缓存受服务条款和额度约束，上线前需要确认账号类型和署名方式；
- 中国省级边界必须使用来源清晰、版本明确的数据；
- 单机部署的主要瓶颈是磁盘、网络和天气场处理耗时，访问量上升后再考虑对象存储或 CDN；
- 真实天气产品需要显示模型运行时间、有效时间和数据来源，避免用户把预报误认为实时观测。
